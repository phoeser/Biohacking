FIRESTORE-REGELN FÜR DIE ERFAHRUNGSBERICHTE
===========================================

!!! NICHT ERSETZEN — NUR ERGÄNZEN !!!

Eine frühere Fassung dieser Datei sagte, man solle die bestehenden Regeln
löschen und komplett ersetzen. Das war falsch und hätte Schaden angerichtet.

Die tatsächlich aktiven Regeln des Projekts sind deutlich umfangreicher als
angenommen. Sie enthalten unter anderem eigene Regeln für:

    users, wearables, vitals, supplementLog,
    recommendations, healthkit, config, oauthStates

mit fein abgestuften Rechten (teils nur lesen, teils nur schreiben, bei
einer Collection getrennte Rechte für create/update und delete). Wer das
durch einen pauschalen Block ersetzt, zerlegt die WHOOP-Anbindung, den
Apple-Health-Import und die OAuth-Verarbeitung — und merkt es erst, wenn
in der App etwas nicht mehr lädt.

Deshalb steht unten nur noch der ZUSATZ. Alles Bestehende bleibt unangetastet.


SO GEHT ES
----------
1. Regeln öffnen:
   Firebase-Konsole → linke Seitenleiste → "Erstellen" aufklappen →
   Firestore Database → Reiter "Regeln".
   (Direkt: console.firebase.google.com/project/biohacking-kompakt/firestore
    — Deeplinks auf den Regel-Reiter leiten manchmal zur Übersicht um, dann
    einfach über die Seitenleiste klicken.)

2. Im Editor die Zeile suchen, die so aussieht:

       match /databases/{database}/documents {

   Sie steht ganz oben, direkt unter "service cloud.firestore {".

3. Cursor ans Ende dieser Zeile setzen, Enter drücken — und den Block
   zwischen den Strichlinien dort einfügen.

   Wichtig: NUR einfügen. Nichts markieren, nichts löschen.

4. Oben rechts auf "Veröffentlichen".

Falls der Editor eine rote Fehlermeldung zeigt: nicht veröffentlichen,
sondern den Fehlertext hierher kopieren. Bis zum Veröffentlichen bleiben die
alten Regeln aktiv, es kann also nichts kaputtgehen.

    // ===== Erfahrungsberichte (ergaenzt 08/2026) =====

    // Wer darf eingereichte Berichte freigeben? Muss mit
    // ERFAHRUNG_ADMIN_EMAILS in js/data/erfahrungen.js uebereinstimmen.
    function istErfahrungsAdmin() {
      return request.auth != null
             && request.auth.token.email_verified == true
             && request.auth.token.email == 'phoeser@web.de';
    }

    match /erfahrungen/{id} {

      // Oeffentlich lesbar sind nur freigegebene Berichte. Angemeldete sehen
      // zusaetzlich ihre eigenen Einreichungen, der Admin sieht alles.
      allow read: if resource.data.status == 'approved'
                  || istErfahrungsAdmin()
                  || (request.auth != null && request.auth.uid == resource.data.uid);

      // Einreichen darf jede angemeldete Person — aber immer nur mit
      // status 'pending' und der eigenen uid. Das verhindert, dass sich
      // jemand selbst freischaltet.
      allow create: if request.auth != null
                    && request.resource.data.status == 'pending'
                    && request.resource.data.uid == request.auth.uid
                    && request.resource.data.substanz is string
                    && request.resource.data.substanz.size() > 0
                    && request.resource.data.substanz.size() <= 120
                    && request.resource.data.text is string
                    && request.resource.data.text.size() > 0
                    && request.resource.data.text.size() <= 4000;

      // Freigeben, ablehnen und loeschen darf nur der Admin.
      allow update, delete: if istErfahrungsAdmin();
    }

    // ===== Ende Erfahrungsberichte =====

WARUM E-MAIL UND NICHT UID
Die UID waere langfristig stabiler, ist aber ein zusaetzlicher Wert, der mit
js/data/erfahrungen.js synchron gehalten werden muesste. Die verifizierte
E-Mail ist derselbe Wert wie dort — eine Stelle weniger, an der etwas
auseinanderlaufen kann. Bei Google-Anmeldung ist email_verified immer true.

Wer lieber die UID will: unter Authentication → Users steht sie in der Spalte
"Nutzer-UID". Dann istErfahrungsAdmin() so ersetzen:

    function istErfahrungsAdmin() {
      return request.auth != null && request.auth.uid == 'HIER_DIE_UID';
    }


VORHER TESTEN
Neben dem Regel-Editor gibt es den "Rules Playground". Dort laesst sich eine
Leseabfrage auf /erfahrungen/beliebig simulieren — einmal ohne Anmeldung,
einmal mit der Admin-Adresse — ohne echte Daten anzufassen.


WENN NICHTS GEMACHT WIRD
Ohne diese Ergaenzung greift die Standardablehnung: Eingereichte Berichte
werden gar nicht erst gespeichert. Die App bleibt sonst voll funktionsfaehig,
nur das Einreichen laeuft ins Leere.
